# DSH 插件介绍 / README 写作

供 Codex / AI 编程助手写 DSH 插件介绍和 README 时使用，让读者先知道能解决什么问题，再看到结果并完成第一次使用。适用于完整 README、插件目录简介和介绍文案；短介绍保留收益与差异，并链接完整上手文档。

致谢：思路借鉴 MIT 资料 [awesome-readme](https://github.com/fralapo/awesome-agent-skills/tree/main/skills/awesome-readme) 与 [copywriting](https://github.com/coreyhaines31/marketingskills/tree/main/skills/copywriting)，本文自写，未复制其实质段落。

## 写之前：确认事实与范围

1. 在用户授权的目录内，定向读取目标插件现有 README、`package.json`、配置及必要的功能入口。确认读者、使用场景、真实能力、包目录名和首次使用入口；不因写文档而遍历其他 worktree 或私密目录。
2. 用一句内部草稿回答：“谁遇到什么问题，用它之后能做成什么？”再列出有依据的差异。已有好文案保留，只修改任务要求的部分。
3. 分清已经支持、计划支持和未验证的内容。缺证据时收窄承诺；不编造性能数字、截图、用户评价、兼容范围或竞品结论。
4. 只修改授权文档。写 README 不代表获准改实现、安装插件、发布 npm、修改全局配置或执行 Git 写操作；遵守本次任务的文件与操作边界。

## 固定阅读顺序

### 1. 第一屏：一句话说清用户能得到什么

标题后立即给出一句价值主张：具体用户动作 + 能获得的结果。读者应在几秒内明白何时会用到它。

- 可写：“帮你判断先修哪个 issue、哪个 PR 值得合，把仓库待办排出先后。”
- 避免先写：“基于增量缓存的只读 GitHub triage 插件，采用……”
- 标题用插件名即可；版本号、技术栈、内部模块和验证信息不能挤占开头。
- 需要补充背景时只加一两句，围绕实际场景，不复述抽象定位或堆“强大、高效、智能、无缝”等形容词。

### 2. 紧接 3–4 条亮点：收益与差异一起写

每条先写用户少做了什么、看清了什么或能决定什么，再用短语解释能力依据。整体必须说明与同类插件相比，在哪个具体环节有区别。

- 采用“收益 + 具体做法”的句式，例如：“少翻多个页面：在一份结果中查看待办及判断依据。”只有实现确实支持时才采用。
- 差异围绕输出内容、适用场景、使用步骤或操作边界，明确比较对象和维度。
- 若没有竞品实测，可比较有依据的工作方式，例如“逐条打开 issue 查看”与“集中查看待办摘要”；不要据此宣称胜过所有同类插件。
- 没有独特性证据就向用户说明缺什么事实，不硬造“唯一”“最快”“全面领先”，也不为凑满条数拆分同一收益。

### 3. 示例输出或截图：让读者看到结果

位置放在亮点之后、快速上手之前。至少提供一种能展示核心结果的内容：

- 文本类插件：给出一次具体输入和对应的简短输出，保留对读者有用的字段与判断依据。
- 界面类插件：放真实截图或短演示，并写清入口、操作及结果；图片使用可访问的相对路径和说明文字。
- 无真实素材时优先给明确标为“示意输出”的文本，不能假装已经运行得到。
- 仅在草稿中允许写“截图位置：展示……”，并说明应截哪个界面。交付 README 前应替换为实际素材或示意输出，移除失效图片与空占位。
- 示例隐藏账号凭据和私人信息；不把演示中的判断写成插件保证正确的结论。

### 4. 三步快速上手：从安装到得到第一份结果

必须恰好用三个编号步骤，覆盖退出桌面端、安装、重开配置与首次使用。实际 README 要替换包名、配置项及入口，不能直接留下下面的模板占位。

1. **完全退出桌面 DSH。** 退出所有窗口，并从系统托盘退出 DSH；确认桌面端已完全关闭，再安装或更新。
2. **在终端安装目标插件。** 本仓库 Git 安装地址必须使用以下格式，`<pkg>` 是 `packages/` 下真实目录名，不一定等于 npm 包名。完整地址必须加引号，避免 PowerShell 把 `&` 当作操作符。

   ```powershell
   dsh plugin --profile desktop add "github:hzopc1031/dsh-plugins#main&path:/packages/<pkg>"
   ```

   例如，只有确认目录是 `dsh-github-triage` 时才写：

   ```powershell
   dsh plugin --profile desktop add "github:hzopc1031/dsh-plugins#main&path:/packages/dsh-github-triage"
   ```

   本仓库默认面向桌面环境，使用 `--profile desktop`。若已核实读者使用其他 profile，再按实际情况改写；不要猜测或拼入未确认的参数。
3. **重新打开 DSH，得到第一个结果。** 写清从哪里启用或进入插件、必填配置、一次最小操作或自然语言指令，以及成功后能看见什么。若需要外部账号或令牌，说明必要权限及填写位置，不提供真实凭据。

影响安装的最低前提应在相关步骤旁简短交代；详细兼容版本、支持矩阵和限制仍放文末。安装地址与命令是文档内容，不是让写作者执行安装。

### 5. 日常使用：按用户任务组织

需要扩展时，按“我要完成什么”写小节，给具体入口或指令及预期结果。参数、配置和 API 表只保留完成任务所需的内容；较长参考资料用链接承接，不让读者先理解内部架构才能使用。

### 6. 最后：版本、限制、实现机制、测试说明

将这些内容集中放在 README 最后一个“补充说明”区域，按需要分小节：

- **版本与兼容：** 插件版本、已核实的 DSH 版本、操作系统或依赖前提；不把单一测试环境扩大为支持承诺。
- **限制与边界：** 支持范围、权限、数据流向、已知问题，以及不适用的场景。首次操作必须知道的权限或风险在操作旁同步提示，详细说明仍留在这里。
- **实现机制：** 增量缓存、读取方式、数据来源、内部架构等，解释它们怎样影响使用；不重复源码结构。
- **测试与验证：** 客观交代验证环境、已验证内容及未验证边界；自动测试通过、安装完成、实际功能可用、界面已检查是不同的结论，不能混用。

禁止把 README 写成验收记录。测试数、`typecheck` 结果、“未实测”、commit hash、逐条执行日志不得堆在开头；只有确实帮助理解当前状态时才在文末简述。开发者验收过程无需逐项搬入 README。

## 术语改成大白话

第一次出现必要术语时先讲用户含义，括号补正式名称；后续保持一致。命令、配置键和产品正式名称保留准确拼写。

| 原写法 | 面向用户的写法 |
| --- | --- |
| triage | 判断待办先后、先看哪些问题 |
| issue / PR | 问题与待办（issue）/ 待合并的代码改动（PR） |
| 增量缓存 | 再次查看时只更新变化的内容，减少重复读取 |
| 只读 | 只查看仓库信息，不修改 issue 或 PR |
| profile | 当前使用的 DSH 环境（profile） |
| Host / Client | 后台处理 / 界面展示；涉及准确接口时再补正式名称 |

以上只是表达示例，不能当作所有插件都具备的能力。“只读”等边界按实现核实后使用，放在相关操作说明或文末，不拿它代替核心价值。

## 好坏对比：dsh-github-triage

以下坏例子概括 0.1.0 旧介绍的技术优先风格，并非旧 README 原文；好例子是文案方向示范，不是新增功能承诺。实际使用前逐项核实能力。

**坏例子**

> dsh-github-triage 0.1.0：支持增量缓存，只读访问 GitHub 数据，提供 issue / PR 聚合和 triage 流程。已通过 typecheck 与若干测试，桌面环境未实测。

问题：读者先遇到版本、机制和验证记录，却看不出它如何帮自己做决定；“聚合”和“triage”也没有解释带来什么结果。

**好例子**

> 帮你判断先修哪个 issue、哪个 PR 值得合，把仓库待办排出先后。
>
> - 把需要关注的问题集中看，方便决定先处理哪一项。
> - 查看待合并的改动时一起看判断依据，方便决定下一步审查什么。
> - 相比逐条翻 GitHub 列表，围绕“下一步处理什么”组织结果，减少来回查找。

随后展示一份“建议关注项 + 原因 + 下一步”的示意输出，再接三步快速上手。已核实的缓存方式、只读边界、版本及验证情况放文末。若实现只整理信息而不提供排序或判断依据，就把相应承诺收窄为“集中查看 issue 和 PR，方便你自己判断处理顺序”。

## 官方约定在文档中的应用

参考固定版本 [cordis-plugin-development：dsh-v0.2.1-rc.5](https://github.com/deepseek-ai/deepseek-harness/tree/dsh-v0.2.1-rc.5/packages/preset/agent-preset/skills/cordis-plugin-development)，尤其是 [Host 插件说明](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.5/packages/preset/agent-preset/skills/cordis-plugin-development/references/host-plugin.md)：

- README 中的名称、能力和入口应与插件真实情况及插件管理器中的描述一致；本地化标题和说明要能让用户认出插件，不能沿用无关模板文字。
- 配置、包入口和公开接口依据实际文档或实现核实；不要猜安装目录，也不要把内部实现写成稳定的公开接口。
- 安装、启用、重启与可用状态应准确区分。看到安装成功或注册成功，不足以宣称功能或界面已验证；未做的验证在文末如实说明。
- 引用截图、图标等素材前核对真实性、路径和再分发许可，按许可要求署名；不能用模板图冒充插件效果。
- 本 skill 只采用与文档有关的约定，不触发官方 skill 的开发、安装或验证操作流程，也不授权修改插件元数据或显示资源。

## 交付前自检：必须逐项勾选

写完 README 后，复制本清单到本次回复或用户允许的审阅位置，逐项核对并勾选 `[x]`；不额外创建检查文件。不适用项须说明原因；未通过项保持 `[ ]`，修改后复查，不能直接整份预勾。

- [ ] 第一屏紧接标题的一句话说明了用户能得到什么，未先讲实现细节。
- [ ] 有 3–4 条各不重复的亮点，每条以具体用户收益表达。
- [ ] 与同类插件或现有做法的差异清楚，比较有依据且没有夸大。
- [ ] 亮点后有示例输入与输出，或真实截图/演示；示意内容已标注。
- [ ] 图片、链接和锚点有效，没有失效素材或未替换的占位符。
- [ ] 快速上手恰好三步，明确先完全退出桌面 DSH（含托盘）再安装，随后重开使用。
- [ ] Git 地址严格采用 `github:hzopc1031/dsh-plugins#main&path:/packages/<pkg>` 格式，已换成真实目录名，整段地址加引号。
- [ ] 首次使用入口、必填配置、最小操作及可见结果足够具体，profile 如有要求已核实。
- [ ] 术语先用大白话解释，命令和配置键准确，没有空泛宣传语。
- [ ] 版本、详细限制、实现机制和测试说明集中在最后；必要操作提醒在步骤旁可见。
- [ ] 开头没有测试数、typecheck、未实测、commit hash 或验收日志。
- [ ] 所有能力及兼容性承诺都有依据，安装、运行和界面验证的结论没有混淆。
- [ ] 名称、描述、入口与插件实际情况一致，示例和素材没有凭据或私人信息。
- [ ] 只改授权文档，未因写作而执行安装、发布或未授权的 Git 写操作。
